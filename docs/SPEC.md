# Férový nájem — MVP Spec

> Working name. iOS app for renters in Czechia: "check before you pay the deposit".
> Status: pre-development. Items marked **[VERIFY]** are assumptions that must be confirmed against the real source before building on them.

## 1. Problem

Renters in Prague/Brno (20–40 y.o., incl. expats) must decide fast (~38 responses per listing in Prague) and often pay a deposit before they can verify anything. Fraud pattern: fake landlord uses someone else's flat, real photos, sometimes the real owner's name, collects deposits from several people, disappears.

The renter can't quickly answer:
1. Is the price normal? (too high = overpaying; far too low = scam bait)
2. Does the flat exist as a residential unit, and is there a pending cadastral proceeding on it (plomba)?
3. Is the landlord company real and solvent?
4. Are there address risks (flood zone)?
5. Does the deal follow typical scam patterns?

## 2. Solution (MVP)

User enters address + rent + size + disposition and gets a **traffic-light report**:

| Block | Source | Output |
|---|---|---|
| Price | MF Cenová mapa nájemního bydlení | Asking rent vs. MF reference rent (model) for the territorial unit + size category, both directions (overpriced / suspiciously cheap); raw asking min/median/max as context |
| Property | ČÚZK API KN | Building found by address; unit with that number exists; unit use = byt vs. ateliér / nebytový prostor; plomba on unit or building + řízení type/status (V = vklad → ownership/lien change in progress = strong signal). **Liens, executions and easements are NOT available** (they live on LV parts C/D, API returns only the LV number) |
| Landlord (company) | ARES + ISIR | Exists, active, statutory info, insolvency yes/no |
| Address risk | Flood zones (VÚV TGM, declared Q100 + aktivní zóna) | In / near zone (indicative) |
| Scam patterns | Questionnaire (on-device) | Red flags: deposit before viewing, video-only viewing, foreign account, "owner abroad", pressure to pay now, price far below map |
| Owner check | User's own eID | Deep link to nahlizenidokn.cuzk.gov.cz + step-by-step "compare the name with the person you're talking to" |

Monetization (v1.1): free traffic light; full report (details + PDF/share) 79–99 Kč via StoreKit consumable. Subscription later only if there's a monitoring feature.

## 3. Non-goals (MVP)

- Showing or storing owner names (legally blocked — see §8).
- Scraping Sreality / Bezrealitky / Facebook. No listing database.
- Listing-link parsing (v1.1, on user action only, single page, nothing stored).
- Reverse image / duplicate-photo search (v2 — needs a photo source we don't have).
- User accounts, login, Android, web client (a landing page is fine). The backend is still built client-agnostic so a web client can be added later without API changes (§4.1).
- Payments (v1.1).

## 4. Architecture

```
iOS (SwiftUI)  ──HTTPS──▶  Backend (FastAPI)  ──▶  Postgres + PostGIS
                                │
                                ├─▶ ČÚZK API KN (ApiKey, server-side only)
                                ├─▶ ARES REST
                                ├─▶ ISIR_CUZK_WS (SOAP, port 8443)
                                └─ ingested: MF rent map (XLSX), RÚIAN addresses, flood zones
```

- Backend is mandatory: the ČÚZK API key must never ship in the app; datasets need ingestion.
- Stateless report generation; no personal data persisted. Logs: no addresses linked to device IDs beyond short-lived debug logs.
- Hosting: small VPS or Fly.io / Railway. Docker image, IaC optional (Terraform).

### 4.1 API-first, client-agnostic

- The public HTTP API (`/v1/...`) is the product contract; iOS is just the first client. A web client must be addable later with no API changes.
- OpenAPI schema generated by FastAPI is the source of truth for clients; breaking changes only via a new version prefix (`/v2`).
- No iOS-specific fields in requests/responses. User-facing texts are returned as stable codes + parameters (e.g. `flag: "price_far_below_median", ratio: 0.62`); clients localize. Optional `Accept-Language` (cs/en) for the disclaimer and server-rendered text.
- CORS allowlist from config (empty in MVP).
- Client attestation is a pluggable layer (§4.2), not baked into endpoints.

### 4.2 Backend protection

Goal: stop the public backend from being used as a free proxy to API KN (quota burn) and from bulk scraping of reports.

- **Client attestation** (pluggable providers, selected per request by header):
  - `app_attest` — Apple App Attest: attestation verified once per key (Apple cert chain, app ID, counter), then per-request assertions on `/v1/report`. Requires a real device (not Simulator) and a paid Apple Developer account.
  - `devicecheck` — fallback for devices where App Attest is unsupported; weaker, used only for rate-limit identity.
  - `web` — reserved for the future web client (e.g. Cloudflare Turnstile). Not implemented in MVP.
  - Rollout: M2 — provider interface + `disabled` mode (dev/Simulator); M4 — `app_attest` enforced for production iOS builds.
- **Rate limiting** (limits in config, not hard-coded):
  - per IP: all endpoints (e.g. suggest 60/min, report 10/h);
  - per device (attested key id): report e.g. 20/day;
  - global: daily budget of API KN calls; when exceeded, reports degrade gracefully (property block = "temporarily unavailable"), never fail entirely.
  - Counters are short-lived (TTL ≤ 24 h), keyed by IP / key id only — never linked to addresses or report content. Key id is a pseudonymous identifier; no other device data stored.
- **API KN response cache** (Postgres table, key = endpoint + id/kod):
  - positive results (building, unit, parcel, řízení): TTL 24 h;
  - negative results (404 / empty search): TTL 6 h — they also count against quota;
  - codebooks (CiselnikyISKN): TTL 7 d;
  - cache holds only API KN data (no personal data per vyhl. 358/2013 § 14a), no request metadata.
- **Quota watch**: periodic `StavUctu` check; log + alert at 70 % / 90 % of period quota.

### 5.1 API KN — verified endpoints and lookup flow

Relevant endpoints (base `/api/v1`):

| Endpoint | Params | Use |
|---|---|---|
| `GET /Stavby/AdresniMisto/{kod}` | RÚIAN kód adresního místa | **Entry point**: address → building |
| `GET /Stavby/{id}` | ISKN id | Full building |
| `GET /Stavby/Vyhledani` | KodCastiObce, TypStavby, CisloDomovni | Fallback lookup |
| `GET /Jednotky/{id}` | ISKN id | Full unit |
| `GET /Jednotky/Vyhledani` | KodCastiObce*, TypStavby*, CisloDomovni*, CisloJednotky* | Unit by natural id |
| `GET /Parcely/{id}` | ISKN id | Not needed for reports: k.ú. is already in `Stavba.parcely[].katastralniUzemi` |
| `GET /Rizeni/{id}` | ISKN id | Proceeding details |
| `GET /Rizeni/PrijateDne` | TypRizeni, KodPracoviste, DatumPrijeti | Proceedings received on a day (used only to sample `stav` values) |
| `GET /AplikacniSluzby/StavUctu` | — | Quota / period |

Response schemas (fields):
- `Stavba`: id, typStavby, cislaDomovni, castObce, docasna, typyVazby, obec, lv, pravoStavby, definicniBod, **jednotky**, zpusobVyuziti, zpusobyOchrany, **parcely**, adresniMista, **rizeniPlomby**
- `Jednotka`: id, cisloJednotky, typJednotky, **zpusobVyuziti**, zpusobyOchrany, podilNaSpolecnychCastechDomu, lv, vymezenaVeStavbe, **rizeniPlomby**
- `Rizeni`: id, **typRizeni**, poradoveCislo, rok, kodPracoviste, **datumPrijeti, stav**, stavUhrady, provedeneOperace, navazanaRizeni, poznamky
- `LVDef`: id, cislo, katastralniUzemi — number only, no content
- Envelope: data, zpravy, aktualnostDatK, provedenoVolani. 404 for unknown id; 200 + empty list for searches with no match.

Flow:
1. User picks address → `kod adresního místa` (RÚIAN autocomplete).
2. `/Stavby/AdresniMisto/{kod}` → building: `jednotky`, `parcely`, `rizeniPlomby`.
3. Building `parcely[0].katastralniUzemi` → k.ú. code (+ `obec`) → MF rent map lookup. No extra call.
4. Unit number (číslo jednotky, e.g. 1234/12) is **optional**.
   - Given: match in `jednotky` → `/Jednotky/{id}`. **`cisloJednotky` is encoded as `cisloDomovni × 10000 + unit`** (1403/24 → `14030024`); match against every `cislaDomovni` of the building.
   - Deep link for the guided owner check: `https://nahlizenidokn.cuzk.gov.cz/ZobrazObjekt.aspx?typ=Budova&id=<ISKN id>` (verified 2026-11-14); `typ=Jednotka&id=<ISKN id>` by analogy (site is bot-protected, not fetched). Never fetch Nahlížení server-side.
   - Not given: building-level check only (building found, building-level plomby, k.ú.); report says so and shows the hint: *"Ask the landlord for the unit number (číslo jednotky) or LV number. A genuine owner can give it right away."* (cs/en via codes).
   - Building has no units (whole-house ownership): skip the unit check and say so.
5. For each item in `rizeniPlomby` (unit and building) → `/Rizeni/{id}` → type + status + date.

Signals:
- Unit not found under that building/number → yellow ("couldn't confirm the unit; ask landlord for číslo jednotky / LV").
- Unit `zpusobVyuziti` (codebook `ZpusobyVyuzitiJednotky`, verified 2026-11-14): 1 byt → ok; 2 ateliér, 3 garáž, 4 dílna nebo provozovna, 5 jiný nebytový prostor, 8 skupina nebytových prostorů → yellow ("not registered as a flat"); 6 rozestavěná jednotka → yellow ("registered as unfinished"); 7 skupina bytů, 9 skupina bytů a nebytových prostorů → yellow ("registered as a group of units, not a single flat").
- `typJednotky` (codebook `TypyJednotky`): 1 byt nebo nebytový prostor, 2 rozestavěný…, 3 vymezená podle zákona o vlastnictví bytů, 4 vymezená podle občanského zákoníku. Informational only.
- `typRizeni` is an enum in the OpenAPI, no codebook endpoint: V vklad, Z záznam, PGP potvrzení GP, PD podací deník, ZPV pomocné řízení V.
- `stav` is **free Czech text, not a code**, filled only for some types. Observed: "U nemovitostí byla vyznačena plomba" (V, in progress), "Řízení bylo ukončeno" (finished). `provedeneOperace[].nazev` e.g. "Založení řízení", "Zaplombování", "Provedení záznamu", "Ukončení řízení". Rule: an entry in `rizeniPlomby` = in progress unless `stav` = "Řízení bylo ukončeno"; unknown `stav` texts are treated as in progress and logged.
- Active V on unit → red ("ownership or lien change in progress"); V on building, or Z / PGP / PD / ZPV anywhere → yellow with plain explanation.
- Unit number not given → property block reports `check_level: building`, no colour penalty by itself (missing input ≠ risk).
- **Quota (verified 2026-11-14): 500 calls per day** (`aktualniObdobi` = date). `StavUctu` itself is not counted. API key expires after ~6 months (`expiraceApiKey`) → alert 30 days before.
- **Calls per report** (verified): building 1 + unit 1 + 1 per plomba → typically 2, 3–4 with proceedings; codebooks cached 7 d. Without cache ≈ 150–250 reports/day → enough for beta; ask ČÚZK about a higher limit before public launch.

### 5.2 MF rent map — verified file structure (2026-11-14)

Checked against `2026-11-15_Cenova-mapa.xlsx` (Q3 2026, published 2026-11-11) and older files.

- **Download**: `https://mf.gov.cz/assets/attachments/YYYY-MM-15_Cenova-mapa[_v02].xlsx`, MM ∈ {02,05,08,11}; suffix varies → no stable "latest" URL. Ingest discovers the first `*_Cenova-mapa*.xlsx` link on the infografika page (one official page fetch per run, not portal scraping) or takes the URL as a CLI argument. 32 historical files back to 2019, recomputed in July 2026 with the current method.
- **Sheets**: `Základní informace` (definitions, reference sizes, surcharges), `Cenové mapy nájemného` (7 630 rows, 43 columns; headers repeat per block → parse by position).
- **Territorial unit is mixed**: obec for most of CZ (6 048 rows), **k.ú. for Praha and ORP towns** (1 582 rows, 206 towns; Praha = 112 k.ú.). Column `Kód obce` holds the **obec code** in obec rows but the **k.ú. code** in k.ú. rows (k.ú. column filled). Lookup: try k.ú. code from API KN, then obec code.
- **Size category (VK)** by disposition: 1 = 1+kk, 1+1; 2 = 2+kk, 2+1; 3 = 3+kk, 3+1; 4 = 4 rooms and more. (File says "2+2", "3+3" — MF typos.)
- **Per VK, all integers in Kč/m²/month**: model rent of the reference flat (hedonic model), its 95 % lower/upper interval, model rent for a new-build (≤ 5 y), raw asking min / max / median, data coverage 1–5 (0–30 / 31–60 / 61–90 / 90–150 / 150+ observations). No missing values.
- **Service charges: EXCLUDED** (info sheet): "Nájemné v sobě neobsahuje vyúčtovatelné složky, které jsou standardně hrazeny spolu s nájemným jako např. energie, voda, odpad atd." Stated for model values; unclear for raw min/max/median. → Input asks for rent **without** zálohy.
- **Reference flat** is unfurnished, no balcony/terrace/garage/lift, older than 5 years. Surcharges in Kč/m² are **national, per VK**, with a separate table for new-builds (info sheet rows 51–62). Q3 2026, older flats, VK1–4: balcony 16/8/4/8, terrace 36/38/34/26, furnished 30/32/27/23, garage 45/49/38/33, lift 41/45/48/61. Reference sizes per kraj and VK (Praha: 35/53/71/88 m²).
- **Data quality**: min 150 observations per unit (Praha/Brno/Ostrava 70), missing data filled from neighbours up to 30 km (1 km in the three cities). Coverage = 1 in ~90 % of rows → use coverage as a confidence flag; raw min/max are often pooled from neighbours.
- **Time window**: file text says 5 years (1.10.2021–30.9.2026), methodology says 4 years. Inconsistent; don't rely on it.

### 5.3 ISIR — verified interface (2026-11-14)

- `ISIR_CUZK_WS`, SOAP only, anonymous: `https://isir.justice.cz:8443/isir_cuzk_ws/IsirWsCuzkService?wsdl`. Docs: isir.justice.cz/isir/help/Popis_WS_2_v1_13.pdf. Backend needs egress on port **8443**.
- Operation `getIsirWsCuzkData`; request `ic`, `filtrAktualniRizeni=T` (only ongoing proceedings), `maxRelevanceVysledku=2` (no fuzzy name matching), small `maxPocetVysledku`.
- Result: any returned record = ongoing insolvency; `druhStavKonkursu` gives the stage (MORATORIUM, ÚPADEK, KONKURS, REORGANIZ, ODDLUŽENÍ, …). `kodChyby`: WS2 = not found (clean); WS4 / SQL1 / SERVER1 / SOAP fault = **unknown**, never "clean".
- **Personal data**: response can contain `rc`, `datumNarozeni`, `jmeno`, titles, full address and co-debtors (`dalsiDluznikVRizeni=T`). Keep only `ic`, `druhStavKonkursu`, `bcVec`, `rocnik`, `cisloSenatu`, `nazevOrganizace`, `datumPm*`, `urlDetailRizeni`; drop co-debtor records. **Query ISIR only for legal persons** (`pravniForma` from ARES) — an OSVČ also has an IČO.
- Limits: >3000 req/day or >50 req/min may get the client banned → cache per IČO (1 h, matches ISIR sync).
- ARES alternative: `seznamRegistraci.stavZdrojeIr` (AKTIVNI / HISTORICKY / NEEXISTUJICI …) — semantics undocumented, no stage. Optional pre-filter only.

### 5.4 Flood zones — verified source (2026-11-14)

- VÚV TGM "Záplavová území" (metadata `CZ-VUV-MD-ZaplavUzemi`), aggregated from zones declared by water authorities (§66 vodní zákon). Coverage is incomplete by nature; polygons are "pouze orientační" → report wording: indicative, binding extent from the vodoprávní úřad.
- Shapefiles, S-JTSK **EPSG:5514**: Q100 (`E_ISVS$ZAPL_UZ100.zip`, 229 MB) and aktivní zóna (`E_ISVS$ZAPL_UZAZ.zip`, 128 MB) under `heis.vuv.cz/data/webmap/datovesady/isvs/ZaplavUzemi/`. WFS exists (`ags2.vuv.cz/.../isvs_voda/MapServer/WFSServer`) but geometry may be simplified → ingest shapefiles.
- No attribute for return period: the layer defines it → store with `zone_type`. One multipolygon per river (Vltava Q100 ≈ 183 km²) → `ST_Subdivide` before indexing.
- Current version: reference date 2025-08-31; store and show it in the report.
- Prague option (v1.1): IPR Praha open data (CC BY, "data base © IPR Praha") adds category "protected by city flood defences", useful for fair wording.

## 6. Backend API (implemented in M2; contract = `/openapi.json`)

```
GET  /v1/address/suggest?q=...           → [{ruian_code, label, lat, lon}]
POST /v1/report
     { ruian_code, unit_number?, rent_czk, area_m2, disposition, landlord_ico?,
       features{ lift, balcony, terrace, furnished, garage, new_build }, answers{ <question>: bool } }
     (unknown fields → 422)
     → { overall: green|yellow|red,
         price:     { status, asking_per_m2, reference_per_m2, band_low, band_high, raw_min, raw_median, raw_max, coverage, ratio, unit_name, unit_kind: ku|obec, size_category, period },
         property:  { status, check_level: unit|building, building_found, unit_found, unit_use, proceedings[{type, status, received, scope: unit|building}], hints[], kn_deeplink, data_as_of },
         landlord:  { status, name, active, insolvency } | null,
         address:   { status, flood_zone: none|near|q100|active, data_as_of },
         scam_flags:{ status, flags[] },
         disclaimer }
GET  /v1/health
```

Each block carries `status` (green|yellow|red|unknown), `available`, stable signal codes and raw facts; see `app/api/v1/schemas.py`. A block whose source is down or over quota is `unknown` / `available: false`; the report itself always returns 200.

Landlord rules (MVP, decided 2026-11-14): ARES first. Natural persons (ARES `pravniForma` 101, 102, 105–108, 424, 425, or unknown) → no name returned, no ISIR query. Legal persons → ISIR only if ARES `stavZdrojeIr` ≠ NEEXISTUJICI (verified: AKTIVNI for a company in konkurs, NEEXISTUJICI for a clean one). Insolvency in progress or company not active → red.

Address rule: flood check uses the building's definiční bod from API KN (any address in CZ), fallback to RÚIAN point. Inside aktivní zóna / inside Q100 / within `flood_near_m` (default 100 m) → yellow, with "indicative" wording.

Logging: access log without query string or client IP; httpx request logging off (URLs contain address codes).

`unit_number` is optional (§5.1 step 4). Headers: `X-Client-Attestation` (provider + assertion, §4.2), `Accept-Language`.

Anti-fraud signal **`unit_number_withheld`**: raised from the questionnaire answer "the landlord did not give me the unit number / LV when asked" (not from an empty input field). Shown in `scam_flags` as yellow, with the hint above. Wording: "A genuine owner can usually provide this immediately."

### Scoring (initial, tunable — keep thresholds in config)

Price ratio = asking rent per m² (without service charges) / expected rent, where expected = MF **reference rent (model)** for the territorial unit + size category (new-build model if `new_build`) + Σ MF surcharges for the selected `features`. Raw asking median/min/max are shown as context only (often pooled from neighbours). Low coverage (1–2) → show "limited data" and cap the price block at yellow.
- `< 0.70` → **red** ("suspiciously cheap — common scam pattern")
- `0.70–0.85` → yellow
- `0.85–1.15` → green
- `1.15–1.30` → yellow
- `> 1.30` → red ("well above the MF reference rent")

Overall = worst of blocks, except price-overpriced alone caps at yellow (it's information, not danger). Any scam flag or a "suspiciously cheap" price → red, except `unit_number_withheld` alone → yellow (flag severities in config).

Wording: never "unfair"/"scam" as a verdict about a person. Use "X % above the MF reference rent", "matches a common scam pattern".

## 7. iOS app (SwiftUI)

Screens:
1. **Onboarding** (1 screen): what it checks, what it doesn't.
2. **Input**: address autocomplete → optional unit number (číslo jednotky; helper text: "Don't have it? We'll check the building. Ask the landlord for it.") → rent without service charges → area → disposition → features (lift, balcony, terrace, furnished, garage/parking, new build) → optional landlord IČO.
3. **Scam questionnaire**: 5–7 yes/no questions, incl. "Did the landlord refuse or avoid giving the unit number / LV?" (→ `unit_number_withheld`).
4. **Report**: traffic light per block, expandable details, "Check owner yourself" guided flow (deep link to nahlizenidokn + checklist).
5. **About / disclaimer / sources** (CC BY attribution for ČÚZK, ČHMÚ etc.).

- Languages: Czech + English from day one (String Catalog).
- iOS 17+. No accounts. Recent checks stored locally only.

## 8. Legal constraints (hard rules)

- Do not fetch, display or store owner names. API KN doesn't return them; WSDP + "šíření" permit is out of scope (cost, per-user eID, 5-year logs).
- No scraping of portals (Sreality ToS + robots.txt prohibit it).
- No persistent personal data; GDPR review before launch.
- Disclaimer on every report: "orientační informace, není právní posouzení".
- Lawyer consultation (GDPR, katastrální zákon §§ 52–55) before public launch.
- Attribution for CC BY sources.
